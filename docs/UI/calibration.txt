~10/7/2026~ 
2:14pm
The update adds a nine-point calibration preview with the mouSEE logo as the active target, progress display, and navigation. It exposes backend hooks for calibration start, target presentation and acceptance, completion, and cancellation. The backend can also report progress and status to the window.
The tracker process is now managed by a shared TrackerClient, and the overlay consumes tracker events from it. Calibration capture, calculation, and persistence are not included yet; this provides the UI and integration points for that work. The project builds successfully.

~10/10/2026~ 
11:05pm
The setup screen checks the tracker’s frames and tells the user whether a face and both eyes are detected, and why not if they aren’t. Then the mouSEE logo moves to 9 positions across the screen. At each one, the logo shrinks onto the point and a ring fills while the user keeps looking at it. If tracking is lost for half a second (for example the face leaves the camera view, the head turns too far, or the eyes close or are covered), a warning appears, and it also warns if the tracker stops responding. The results screen shows how many targets were captured with both eyes tracked, how stable the tracking was, how long the run took, and Accept and Try again buttons. These numbers come from real tracker frames.
The front end works, but it is not a working calibration yet. Nothing collects the eye data or maps it to screen positions, so the accuracy tile says “Not measured” and a good run shows “Unverified” instead of “Pass”. Still to build: a collector that stores eye data during each target’s capture, a model that maps it to a screen position, a validation step that measures error on four extra check targets (switched on with RunValidation), a gaze predictor for the optional Test tracking screen, and saving the result when the user accepts. Most of this can go in the app/Calibration folder, but where the saved result lives depends on how the app reaches the database.
